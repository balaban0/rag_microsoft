# Testing and Evaluation

A RAG assistant should be tested with both questions it can answer and
questions it should refuse, to confirm it is actually grounded in its
documents rather than guessing. This project's `evaluate.py` script
implements that: it runs a fixed set of "answerable" questions (checking
that the expected source document is retrieved) and "unanswerable"
questions about topics outside the knowledge base (checking that the
assistant declines instead of fabricating an answer), plus edge cases
like blank input and vague, non-specific questions.

Running `python evaluate.py` writes a pass/fail report with response
times to `TEST_RESULTS.md`. Because answers are generated by a language
model, the report's checks are approximate rather than exact string
matches: answerable questions pass based on which source document was
retrieved, and unanswerable questions pass based on a broad set of
refusal keywords, since the model paraphrases its refusal differently
each time rather than repeating the system prompt verbatim.

Response time is also tracked, since the program's target is roughly
1-3 seconds per question on a typical laptop; slower responses point to
using a smaller model, retrieving fewer chunks, or hardware without GPU
acceleration.
